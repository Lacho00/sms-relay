# sms-relay v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Each task names the model to dispatch it to. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Cloudflare Worker that ingests SMS from sms-forwarder, stores each one once in D1, and forwards it to Telegram and/or a signed webhook through a retrying outbox.

**Architecture:** One Hono app (`createApp(deps)`) for HTTP and one `scheduled` handler for the cron. Pure modules (config, identity, schema, backoff, filters, formatting, signing) sit under a thin D1 repository built with Drizzle. Outbound HTTP and the clock are injected (`deps.fetch`, `deps.now`), so tests run with no network and fixed time.

**Tech Stack:** TypeScript 5.9.3 strict, Hono 4.13.13, Zod 4.6.5, Drizzle ORM 0.45.4 + drizzle-kit 0.31.11, D1, Wrangler 4.149.0, Vitest 4.1.11 + @cloudflare/vitest-plugin 1.4.0 + @vitest/coverage-istanbul 4.1.11, Node ≥ 24.

**Spec:** `docs/superpowers/specs/2026-11-09-sms-relay-design.md`. Executors read the spec and this plan. The spec gives every status code, error code, limit and config name. This plan does not repeat them.

## Global Constraints

- Exact versions above, pinned without `^` or `~`. Runtime deps: `hono`, `zod`, `drizzle-orm` only.
- Node 24 must be on `PATH` for every Node command.
- Never return a 3xx. Success is always exactly 200. Terminal rejections on ingest are only 400 and 401.
- Never log an SMS body, a sender, a token, a secret, a URL with a token, or a chat id. Use `log()` from Task 3 only.
- No text, data or logic from other private projects. No company, client or local-domain names anywhere.
- Code, comments, commit messages and docs in English. Conventional commits (`feat:`, `fix:`, `test:`, `docs:`, `ci:`, `chore:`), small. No `Co-Authored-By` or "Generated with" lines.
- No `git push`, no GitHub repo creation, no `wrangler deploy` and no `wrangler d1 create --remote` during this plan.
- Never install Playwright or browsers.
- Every task ends with `npm run verify` green. The coverage thresholds start in Task 1.

## Delegation and review

Rule: the cheapest model that can do the task well. I (the session model) plan, dispatch, check each result against the spec, and fix small problems.

| Model | Used for |
|---|---|
| haiku | mechanical work with a fixed shape: pure functions with complete test tables, config files, CI YAML |
| sonnet | normal feature work: routes, repository, destinations, docs |
| opus | the two tasks where a subtle bug loses or duplicates SMS: ingest atomicity/dedup (Task 7) and the outbox lease/retry loop (Task 12) |

Review: the global rule says every review uses OCR (`ocr-review` skill), never the generic reviewer agents. So the per-task "fresh reviewer" of subagent-driven-development becomes: (1) I check the task's diff against the spec and the Interfaces block, (2) `npm run verify`, then (3) an OCR review at the end of each phase, on the phase diff (`git diff <phase-start>..HEAD`). Findings get fixed before the next phase starts.

## Review Focus

1. **Emoji and other astral characters in the body.** Telegram cutting at 4 096 must not split a surrogate pair. The test is in Task 9.
2. **`received_at` in seconds instead of ms** (a common custom-template mistake): `1762697001` is before 2000, so the request is rejected. The 400 `message` must say `received_at: expected epoch milliseconds or ISO 8601 with zone`, so the user can fix the template. The test is in Task 5.
3. **Authorization header variants:** scheme in any case (`bearer`), extra spaces around the token. These are accepted. `Bearer` with an empty token and `Basic …` are rejected with 401. The test is in Task 3.
4. **JSON that is valid but not an object** (`[]`, `"x"`, `null`, `42`): 400 `validation_failed`, never 500. The test is in Task 7.
5. **Telegram group and channel chat ids:** `-1001234567890` and `@my_channel` are valid. `abc` is a config error. The test is in Task 2.
